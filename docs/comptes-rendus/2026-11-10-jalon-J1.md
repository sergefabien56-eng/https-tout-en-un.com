## 3. Décisions prises et écarts par rapport au plan

| Sujet | Décision | Justification |
|---|---|---|
| **TypeScript 5.9** au lieu de 7.0 (dernière version installée) | rétrogradé et épinglé | TypeScript 7 fait échouer le chargement de `next.config.ts` (`Cannot read properties of undefined (reading 'fileExists')`). Constaté, pas supposé. |
| `next.config.mjs` au lieu de `.ts` | conservé | même cause ; commentaire explicite dans le fichier |
| **`citext` abandonné** | remplacé par un index unique `lower(email)` | `citext` n'est pas une extension garantie ; l'index fonctionnel donne la même garantie sans dépendance |
| **Ordre des migrations modifié** : boutiques (0002) **avant** identité (0003) | assumé | `user_roles.shop_id` référence `shops` ; l'ordre inverse aurait imposé une FK ajoutée après coup |
| **Contraintes ajoutées non prévues au document** | `shops_country_currency_ck`, `marketplace_apps_refresh_tuple_ck`, unicité `NULLS NOT DISTINCT` sur `user_roles` | trouvés **en écrivant les tests** : une devise incohérente avec le pays passait, un « demi-secret » chiffré aussi. | **`app_settings` déplacé en 0004** (au lieu de 0005) | regroupé avec le journal d'audit | une seule migration « plateforme », moins de migrations vides |
| Migrations 0007–0009 du plan (notifications, agrégats, jobs) | **non écrites** | règle R2 : aucune table vide « pour plus tard ». Elles arriveront avec leurs modules (L9, L10) |

| Décisions de design validées sans réponse aux 3 questions | appliquées : menu **complet** par défaut, densité **confort**, paliers recalculés avec `railForcedBelow: 1280` et `drawerPanelBelow: 1440` | modifiables dans `src/core/config/app.config.ts` (un seul endroit, testé) |

## 4. Limites connues et dette technique

1. **PGlite ≠ PostgreSQL 16** : il valide le SQL, les contraintes, la RLS et les triggers, mais pas les extensions (`pg_trgm`, `unaccent`), ni les index GIN trigram, ni la performance. La CI comble ce trou ; **je ne prétends pas que les migrations sont validées sur PostgreSQL 16 tant que le job CI n'a pas tourné**.
2. **Pas de Drizzle** pour l'instant : les tables sont en SQL versionné, sans mapping TypeScript. Le choix reste ouvert (voir §5) ; les tests n'en dépendent pas.
3. **Pas d'authentification** : `users`/`sessions` existent en base, mais aucune route de connexion. L'application est donc actuellement une page statique sans accès protégé (aucune donnée exposée).
4. **La page `/` est une page de démarrage** assumée : elle liste ce qui existe et ce qui n'existe pas, sans aucun chiffre. Elle disparaît au lot L8.
5. **7 vulnérabilités modérées restantes**, toutes dans l'outillage de lint (`typescript-eslint` → `minimatch`, ReDoS). Aucune n'est dans le chemin d'exécution de l'application. `npm audit --audit-level=high` passe.
6. **Pas de tests de charge** : sans données, ils n'auraient aucun sens.
7. `scripts/db-roles.sql` n'a jamais été exécuté (nécessite un PostgreSQL réel) — à valider en L11.

## 5. Points à vérifier et décisions qui vous attendent

1. **Réponses aux 20 questions** de `docs/questions-ouvertes.md` — vous avez validé la Phase 0 sans les renseigner ; j'ai donc appliqué les valeurs par défaut (XOF, CI+SN, densité confort, menu complet, monoorganisation). Les 3 premières (pays, accès API, volumes) changent le schéma et le dimensionnement : **à trancher avant L5**.
2. **Drizzle ou SQL + `pg` brut ?** Je propose Drizzle (typage des requêtes) au lot L5, sans changer les migrations déjà écrites. Dites-moi si vous préférez rester en SQL typé à la main.
3. **TypeScript** : confirmez-vous l'épinglage en 5.9 (stable) plutôt que la version 7 ? C'est un choix de stabilité, réversible.
4. **Politique d'audit** : le seuil bloquant est `high`. Voulez-vous `moderate` bloquant aussi (plus strict, plus de frictions avec l'outillage) ?
5. **Nom de domaine + VPS** : sans eux, L11 ne peut pas être livré et la P1 ne sera pas « Terminée » au sens de la Définition.
